# RAG

# 0. Goal
本リポジトリは、単体LLMの限界（ハルシネーション・非公開データの欠落）を外部ツール連携によって克服するエージェント化の過程を整理したものです。各種エージェントの分類に加え、主要ユースケースであるRAG（Vector RAG / GraphRAG）の2手法を比較。クエリ特性（局所的なテキスト類似度検索 vs オントロジー駆動の構造的関係性分析）に応じた使い分けの基準を整え、RAGの実装方針を考えていくものです。後半で、GraphDB上のオントロジーを活用したGraphRAGを実装し、Vector RAGと結果を比較した実験をしています。

# 1. LLMの進化段階とアーキテクチャの階層

LLMは単体では密室の対話エンジンに過ぎず、外部システムやナレッジデータベースと連携するTools（外部機能）を付与することで初めて実務利用可能なAIエージェントへと進化します。

実は、普段私たちがChatで使っているLLMは、正確には『Baseモデル』そのままではなく、それに学習データを加えて調整した 『Instructモデル』 です。Baseモデルはネット上の文章を読み込んで次に続く言葉を予測するだけのモデルなので、そのまま質問しても続きの文章を書き足すだけで対話になりません。

そこで、ユーザーの指示（Instruction）と理想的なAIの回答をペアにしたSFTデータや、良い回答・悪い回答を比較した選好データをBaseモデルに追加学習（ファインチューニング）させています。こうして人間と対話するAIアシスタントとして仕立て直されたのが、私たちが使っているInstructモデルです。

```text
1. Base Model（事前学習モデル：次単語予測のみ）
   │
   │ + [SFT / RLHF（指示対話の学習）]
   ▼
2. Instruct Model（単体/素のLLM：会話・指示追従が可能だが完全密室）
   │
   │ + [Tools / 外部機能の付与]
   ▼
3. AI Agent System（自律型・複合AIシステム）
   │
   ├── 【カテゴリ 1】 API Integrations（外部サービス連携：メール送信、カレンダー操作等）
   |    │
   |    ├── ① コミュニケーション・通知（メール作成・送信、Slack/Teamsへの情報共有）
   |    ├── ② スケジュール・勤怠管理（カレンダーの予定調整、打刻・勤務時間の記録）
   |    ├── ③ タスク・プロジェクト管理（Jira/Trelloのチケット起票、進捗ステータス更新）
   |    └── ④ 事務・バックオフィス処理（経費精算の自動入力、社内申請ワークフローの起動）
   |
   ├── 【カテゴリ 2】 Web Search / Browsing（リアルタイムな公開Web検索）
   └── 【カテゴリ 3】 RAG（検索拡張生成：非公開データ・専門ドキュメントの結合）
        │
        ├── ① Vector RAG（局所的なテキスト類似度検索）
        └── ② GraphRAG（GraphDBオントロジーを活用した構造的・関係性検索）
```

* **単体LLM（Instruct Model）の限界:** 学習時点以降の最新情報や社内の非公開データを保持しておらず、未知のドメインに対してハルシネーション（嘘）を出力してしまう。
* **AI Agentへの進化:** 単体LLMを推論エンジン（脳）として位置づけ、外部知識を参照する**RAG**をはじめとするToolsを周囲に配置することで、信頼性の高い回答を生成可能にする。


### 1-1. AI Agent Architecture & Implementation Scope

AIエージェントシステムにおいて、LLMはテキスト推論エンジンであり、単体では外部システムへの直接アクセス能力を持ちません。エージェントの実装とは、**LLMを取り巻くアプリケーション層（MCP Client / Agent Orchestrator）を構築し、LLMにツールの存在を認識させて協調動作させること**を指します。

今日のFDE（Forward Deployed Engineer）やAIエンジニアの実務において、LLMのファインチューニングを行う機会は限られており、主要な開発領域は**このオーケストレーション層（MCP Clientの実装、ツール定義のバインディング、コンテキスト制御、状態管理）の設計・実装**が中心となっていると考えています。

#### （1）プロンプトとツール定義の送出

アプリケーション（MCPクライアント）が、ユーザーのクエリにシステムプロンプトやツール一覧（JSON Schema）を統合し、LLMの推論エンジンへ入力します。

#### （2）LLMによる判断と意図の出力

LLMがテキストの意味を解釈し、「回答にツールが必要である」と判定した場合、ツールの名前と引数を指定したJSON構造（Tool Call Intent）を出力します。※この時点ではLLMはツールを直接実行していません。

#### （3）外部ツールの代理実行

アプリケーション（MCPクライアント）がLLMから返されたJSONを解釈し、実際の外部ツール（VectorDBやGraphDBなど）へクエリを発行して処理を実行します。

#### （4）Observation（観察データ）の回収

外部ツールでの処理結果（検索結果やレスポンスデータ）がアプリケーションに返却されます。

#### （5）コンテキストの再構築と再問合せ

アプリケーションが回収したデータを会話履歴（Context）に組み込み、「このツール実行結果を踏まえて回答を作成してください」というプロンプトを構築して、再びLLMに入力します。

#### （6）最終回答の生成

LLMが入力されたObservationデータを読み込み、ユーザーの元々の質問に対する自然言語の最終回答を生成してアプリケーションへ返します。（その後、アプリからユーザーへ提示されます）

# 2. 課題解決の2つのアプローチ（RAG vs ファインチューニング）

単体LLMの「知識不足」や「ドメイン適応」を補うアプローチとして、外部ツール連携である**RAG**と、モデル自体の重みを書き換える**ファインチューニング（FT）**が存在します。

| 手法 | 特徴と役割 | コストと運用の特徴 |
| :--- | :--- | :--- |
| **RAG<br>(検索拡張生成)** | **外部の辞書を引きながら答える**手法。<br>社内文書やDBを検索し、その結果をプロンプトに含めてLLMに回答させる。 | **運用低コスト・即時更新**<br>DBを書き換えるだけで最新情報が反映される。初期学習コストは不要だが、検索精度に依存する。 |
| **Fine-Tuning<br>(事前学習の微調整)** | **脳の構造（モデルの重み）を書き換える**手法。<br>特定の専門用語、口調、出力フォーマット（JSON等）をモデル自体に定着させる。 | **初期高コスト・更新難**<br>GPUリソースと高品質な学習データが必要。事実の追加・更新には再学習が必要なため、最新ナレッジの保持には不向き。 |

# 3. RAG手法の選定基準

本リポジトリで扱う **RAG** においては、要求されるデータ構造や問いの性質に応じて使い分けを行います。

1. **Vector RAG（局所的・テキスト類似度検索）**
   * **用途:** 就業規則やマニュアルなど、1つの文書・章節の中に答えが完結しているFAQ型検索や、単一キーワードの類似性に基づく局所的な情報検索。
2. **GraphRAG（構造的・GraphDBオントロジー駆動検索）**
   * **用途:** インフラ構成、依存関係、組織階層など、多段階のリンク（Nホップ）を辿る関係性分析や、GraphDB上のオントロジー定義を活用して正確なドメイン知識を構造的に紐付ける検索。

### 3-1. 従来の Vector RAG（局所的・テキスト類似度検索）が得意なケース

**質問:** 「当社の年次有給休暇の付与日数ルールと、申請期限は何日前までか教えてください。」

| 比較項目 | ① 従来の Vector RAG | ② GraphRAG (GraphDBオントロジー駆動検索) |
| :--- | :--- | :--- |
| **裏側での検索処理** | 「有給休暇」「付与日数」「申請期限」に類似度が高い就業規則の**該当文章チャンク（1〜2節）**を直接取得 | GraphDB上のオントロジー・URIやNホップのリンク（属性含む）を辿り、関連するエンティティと関係性を構造的に抽出 |
| **実際の回答** | 「就業規則第15条に基づき、勤続年数に応じて年10日〜20日の有給休暇が付与されます。また、取得の申請は原則として**取得希望日の3日前まで**に申請システムより提出する必要があります。」 | 「『年次有給休暇』は規定上の `ex:LeavePolicy` に紐づき、勤続年数や申請期限（`ex:deadline 3日前`）のプロパティ構造情報を保持しています。」 |
| **回答の質・課題** | **⭕ 完璧に対応可能（最も低コスト・高速）**<br>単一のドキュメント（就業規則）内に記載された文章をピンポイントで検索・引用するため、正確かつ自然な回答が最小の計算コストで得られる。 | **🔺 構造化データ向き・文章の長文表現には不向き**<br>細かい例外規定や長文のニュアンス全体を自然な文章として復元・解説するのには、グラフ構造よりもテキストそのものを扱うVector RAGの方が適している。 |

### 3-2. GraphRAG（GraphDBオントロジー駆動検索）が得意なケース

**質問:** 「当社におけるセキュリティ上の懸念点や、過去の障害を踏まえた改善策を教えてください。」

| 比較項目 | ① 従来の Vector RAG | ② GraphRAG (GraphDBオントロジー駆動検索) |
| :--- | :--- | :--- |
| **裏側での検索処理** | 「セキュリティ」「障害」「改善策」の単語に類似度の高い数件の文章チャンクのみを取得 | GraphDB上のオントロジーや多段階の依存パス（Nホップのリンク）を辿り、関連するシステム構造や障害・対策の因果関係を抽出 |
| **実際の回答** | 「2025年10月に発生したRedisのメモリ枯渇障害では、セッション保持に影響が出ました。また、一般的な改善策としてはパスワードの定期変更が推奨されます。」 | 「決済基盤（`ex:PaymentService`）はセッションキャッシュ（`ex:SessionCache` / `ex:Redis`）に直接依存しており、依存先の障害波及パスが複数定義されています。また、これに対応するインシデントログや対策ノードがリンクしています。」 |
| **回答の質・課題** | **❌ 局所的で不十分**<br>たまたま検索にヒットした1〜2個の過去ログしか見えておらず、システム全体の依存関係や構造的リスクを網羅・俯瞰できていない。 | **⭕ 依存関係の正確な追跡が得意**<br>複数コンポーネント間の複雑な依存関係や多段階のネットワーク/組織パスを100%正確に辿り、構造的な因果関係や影響範囲を漏れなく特定できる。 |

### 4-1. 多段の依存関係と正確なファクトを問う質問

**質問:** 「`認証機能` が停止した場合、最終的に影響を受けるすべてのサービスと、過去に発生した障害の発生原因を教えてください。」
※（`AuthService` ではなく、あえて表記揺れのある「認証機能」で質問）

| 比較項目 | ① 従来の Vector RAG | ② GraphRAG (GraphDBオントロジー駆動検索) |
| :--- | :--- | :--- |
| **検索メカニズム** | テキストの類似度検索により、「認証機能」に関連する文章チャンクを直接取得 | 表記揺れ（認証機能 ≒ `ex:AuthService`）をラベルマッチング等で吸収し、GraphDB上の多段パス（`dependsOn*`）を決定論的に追跡 |
| **裏側でのデータ処理** | 偶然ヒットしたマニュアルや障害ログの断片的なテキストをそのままコンテキストに統合 | 起点ノード特定後は、データベースレベルで100%正確なノードリンク（`PaymentService`, `OrderService`, `UserPortal`）と障害トリプルを網羅的に取得 |
| **実際の回答** | 「『認証機能』に関連する記述として、UserPortalでのログインエラーに関するログが数件ヒットしました。過去の障害については詳細な因果関係が不明です。」 | 「『認証機能（AuthService）』の影響範囲は **PaymentService, OrderService, UserPortal の3件**です（漏れ率0%）。過去障害の原因は **SessionCache(Redis)のメモリ枯渇（Incident202510）** です。」 |
| **強みと評価** | **❌ 構造的な追跡・網羅性が不足**<br>散在するテキストの断片から多段階の依存関係を正確に繋ぎ合わせることができず、抜け漏れが発生しやすい。 | **⭕ 決定論的な網羅性と正確なファクト追跡**<br>GraphDBのオントロジー・Nホップ構造により、複雑な依存関係や影響範囲を100%正確に特定できる。 |

# 5. RAGの比較実験

以下の架空のドキュメントを、まずはVectorDBとして登録します。
```
=== インフラ・開発チーム雑記＆障害振り返りメモ（未整理） ===

・2025/10/12 インシデント振り返り (INC-202510)
AuthServiceのレスポンスが突如激重になり全系停止した件。
原因調べたら、認証セッションの保持に使ってるRedis（SessionCache）がメモリ溢れ（OOM Kill）起こしてた。セッション検証がタイムアウトしてAuthServiceが死んだのが引き金。
これ、そもそもSessionCacheが1台構成なのが諸悪の根源。マルチAZでクラスタ化して、一時キャッシュとセッションデータ分けようって話出てるけど放置されてる。あと、AuthService死んだときに後続サービスが巻き添え喰らわないようにサーキットブレーカー入れないとまた同じこと起きるぞ。

・依存関係の走り書き（仕様書が古いので各自確認のこと）
- UserPortalはログインのためにAuthService叩く。あと注文履歴表示でOrderService呼んでる。
- OrderServiceは受注時にPaymentServiceのレスポンス待ってから処理進める。
- PaymentServiceは決済トークンの有効性チェックで毎回AuthServiceを直接叩いてる。
- NotificationServiceはOrderServiceからのイベントフックで動いてメール飛ぶ仕組み。

・2024/05/18 インシデント振り返り (INC-202405)
PaymentServiceでスロークエリ多発してDBコネクションが枯渇。
原因は決済履歴テーブルのインデックス貼り忘れ。PaymentServiceが詰まったせいで、レスポンス待ちのOrderServiceも詰まり、最終的にNotificationServiceまで非同期キューが溢れて止まった。
DBのインデックス見直しと定期的なスロークエリモニタリング、コネクションプールのチューニングを改善タスクに入れること。

・2026/01/22 インシデント振り返り (INC-202601)
NotificationService経由のメール送信が全部エラーになった件。
原因は外部APIキーの有効期限切れと、サービス間通信で使ってるIAMロールのポリシー設定ミス。IAMポリシーで `resource: "*"` になってて過剰権限だったから、作業者が意図しないリソースを上書き操作できちゃったのが直接のトリガー。
対策としては、ワイルドカード（*）の全廃と最小権限の原則（PoLP）徹底。IAMロールの定期監査タスクを組む。

・セキュリティ監査の指摘事項（メモ）
本番環境（ProdDB）へのアクセス経路がガバガバ。開発VPCから直接ProdDBにアクセスできるルートが残ってるのヤバすぎる。アクセス経路絞って、Bastion（踏み台）経由＋VPC Peeringで厳格に分離してくれ。
あと上述の通り、IAMポリシーで権限与えすぎ問題と、AuthService/SessionCache周辺のSPOF（単一障害点）放置は早急にインフラチームで対応すること。
```

### セキュリティ上の懸念点

**1. IAMポリシーの過剰権限（INC-202601 / 監査指摘）**
IAMロールのポリシーが `resource: "*"` になっており、作業者が意図しないリソースを上書きできる状態でした。これが2026/01のメール送信全停止の直接のトリガーです。監査でも同様の指摘が出ています。

**2. ProdDBへのアクセス経路（監査指摘）**
開発VPCから本番DBへ直接アクセスできるルートが残っています。誤操作や侵害時の影響範囲が非常に大きい状態です。

**3. AuthService / SessionCache周辺のSPOF（INC-202510 / 監査指摘）**
SessionCache（Redis）が1台構成のため、OOMで落ちるとAuthServiceも停止し、全系停止につながりました。クラスタ化の議論は出ているものの放置されています。

**4. 認証基盤への強い依存（依存関係メモ）**
UserPortalとPaymentServiceの両方がAuthServiceを直接叩いており、PaymentServiceは決済トークンの検証のたびに呼びます。AuthServiceの障害がログインだけでなく決済まで波及する構造です。

### 過去の障害を踏まえた改善策

| インシデント | 原因 | 改善策 |
|---|---|---|
| INC-202510（全系停止） | SessionCacheのOOM Kill、1台構成 | マルチAZでクラスタ化／一時キャッシュとセッションデータの分離／サーキットブレーカー導入 |
| INC-202405（決済〜通知の連鎖停止） | 決済履歴テーブルのインデックス漏れによるコネクション枯渇 | インデックス見直し／スロークエリの定期監視／コネクションプールのチューニング |
| INC-202601（メール送信全断） | 外部APIキーの期限切れ、IAMの設定ミス | ワイルドカードの全廃／最小権限（PoLP）の徹底／IAMロールの定期監査 |
| 監査指摘 | 開発VPCからProdDBへの直接経路 | Bastion（踏み台）経由＋VPC Peeringで厳格に分離 |

### 優先度の考え方（私見）

- **最優先**: SessionCacheのクラスタ化とサーキットブレーカー。全系停止の再発リスクが最も高く、すでに議論が出ているのに止まっています。
- **次点**: ProdDBへのアクセス経路の分離とIAMのワイルドカード廃止。いずれも監査で指摘済みで、侵害や誤操作の影響が大きい項目です。
- **継続タスク**: スロークエリ監視とIAMの定期監査。仕組み化しないと形骸化しやすいため、担当と頻度を決めて運用に乗せるのが良いでしょう。

### 補足

- 外部APIキーの期限切れ（INC-202601の原因の一つ）については、メモ上に具体的な対策が書かれていません。期限監視やローテーションの仕組みを追加で検討する余地があります。
- 依存関係メモ自体に「仕様書が古い」と書かれているため、構成図の最新化も合わせて行うと、今後の障害分析がしやすくなります。

### 5-2-4. GraphRAGでの出力結果

ナレッジグラフ（構造・依存関係）とVectorDB（障害振り返りの原文）の両方を検索し、突き合わせて整理しました。

#### 1. グラフから見えた構造的なリスク

グラフ上の依存関係は次のとおりです。

```
UserPortal → AuthService → SessionCache(Redis)
UserPortal → OrderService → PaymentService → AuthService
NotificationService → OrderService
DevVPC → ProdDB（直接アクセス）
Service IAM Role → ワイルドカード権限
```

- **AuthServiceがハブになっている**: UserPortalとPaymentServiceの両方がAuthServiceに依存し、その下にSessionCacheがあります。SessionCacheが落ちると、実質ほぼ全サービスに影響が及びます。
- **依存の連鎖が深い**: 注文履歴の表示（UserPortal → OrderService → PaymentService → AuthService → SessionCache）は、ログインとは別の機能なのに、4段先のRedisに依存しています。
- **セキュリティ面の逸脱がグラフにも表れている**: DevVPCからProdDBへの直接アクセスと、サービス用IAMロールのワイルドカード権限が確認できます。

#### 2. 過去の障害とグラフの突き合わせ

| 障害 | VectorDBの記述（原因・対策） | グラフによる裏付け |
|---|---|---|
| INC-202510（全系停止） | SessionCacheのOOM Killが引き金。1台構成が根本原因。対策はマルチAZクラスタ化、キャッシュとセッションの分離、サーキットブレーカー | SessionCache → AuthService → 他サービスへと影響が波及する経路が存在する |
| INC-202405（決済〜通知の連鎖停止） | 決済履歴テーブルのインデックス漏れでコネクション枯渇。対策はインデックス見直し、スロークエリ監視、プール調整 | PaymentService → OrderService → NotificationServiceの依存の向きと、停止が伝わった順序が一致する |
| INC-202601（メール送信全断） | 外部APIキーの期限切れとIAMのワイルドカード。対策はワイルドカード全廃、最小権限、定期監査 | IAMロールのワイルドカード権限が現状も残っている |
| セキュリティ監査 | 開発VPCからProdDBへの直接経路。Bastion＋VPC Peeringで分離 | DevVPCからProdDBへの直接アクセスが現状も残っている |

2件の障害は、グラフの依存経路とそのまま重なります。INC-202510とINC-202405は、どちらも「下流の障害が上流に連鎖する」構造的な問題です。

#### 3. 現在も残っている懸念点

1. **SessionCacheの単一障害点**: 1台構成のままで、クラスタ化の話は出たまま止まっています。
2. **障害の連鎖を止める仕組みがない**: サーキットブレーカー未導入のため、一部の障害が全体に広がります。
3. **IAMのワイルドカード権限**: INC-202601の直接の原因が、まだ解消されていません。
4. **ProdDBへの直接アクセス経路**: 開発環境からの誤操作や侵害の影響が本番に届く状態です。

#### 4. 改善策の優先順位（私見）

1. **最優先**: SessionCacheのマルチAZクラスタ化と、AuthService周辺へのサーキットブレーカー導入。ハブ構造のため、効果が最も広く及びます。
2. **次点**: ProdDBの経路分離（Bastion＋VPC Peering）とIAMのワイルドカード廃止。どちらも監査で指摘済みで、影響が大きい項目です。
3. **構造面の見直し**: PaymentServiceが決済トークン検証のたびにAuthServiceを直接呼ぶ点は、トークン検証結果のキャッシュなどで依存を弱める余地があります。
4. **運用の仕組み化**: スロークエリ監視とIAMの定期監査は、担当と頻度を決めて運用に乗せることが必要です。

#### 5. 今回の検索で分かった限界

- **グラフに属性値が入っていません**: SessionCacheのisSinglePointOfFailureやmultiAZ: false、AuthServiceのisCritical、リスクレベル「高」といった値は、グラフに登録されていませんでした（構築時の「属性付与0件」と一致します）。グラフにはこれらの項目名だけがノードとして残っており、単一障害点であることはVectorDBの記述に頼っています。
- **ProdDBとBastionの関係**: グラフのProdDBは、DevVPCからの接続先としてのみ登場しています。
- **外部APIキーの期限切れ**: INC-202601の原因の一つですが、グラフにも振り返りメモにも具体的な対策がありません。期限監視やローテーションの仕組みを別途検討する必要があります。

属性値の欠落を解消したい場合は、属性を文章の形（例:「SessionCacheは単一障害点である」）に書き直して再登録する方法があります。必要でしたら、その修正版のテキストを作成します。

### 6-2. 決定的な違いを生んでいる3つのポイント

#### 構造的リスクの「見え方」と説得力

* **VectorDB単体:**
「UserPortalとPaymentServiceの両方がAuthServiceを叩いている」という事実をテキストベースで把握しています。ただし、それがシステム全体の中でどれほどクリティカルな「ボトルネック（ハブ）」であるかは、読み手の推論に依存します。
* **GraphRAG（ハイブリッド）:**
依存関係をテキスト形式のパス（`UserPortal → OrderService → PaymentService → AuthService → SessionCache`）として明示することで、**「ログインとは無関係の注文処理が、なぜか4段先のRedisに依存している」という構造の歪み**を視覚的・論理的に浮き彫りにしています。これにより、SessionCache対策の最優先度に対する説得力が跳ね上がります。

#### アーキテクチャ改善案の「一歩進んだ提案」

* **VectorDB単体:**
過去の障害メモや監査指摘に書かれている対策（クラスタ化、サーキットブレーカー、ワイルドカード廃止など）を綺麗に整理・分類して終わっています。
* **GraphRAG（ハイブリッド）:**
グラフ上のハブ構造（PaymentServiceが直接AuthServiceを叩いている点）から派生して、**「トークン検証結果のキャッシュなどで依存を弱める余地がある」という、テキストメモには直接書かれていない構造的・設計的な改善案**を自発的に提案できています。

#### ツールの限界に対する「客観的な自己認識」

* **GraphRAG側の特筆すべき点（項目5）：**
5-2-4の結びにおいて、**「グラフに属性値（`isSinglePointOfFailure` や `multiAZ: false` など）が入っていなかった（属性付与0件）」という技術的制約・限界を正確に自己申告**しています。
AIが「すべて完璧にグラフから読み取りました」とハルシネーションを起こすのではなく、**「グラフは構造（接続）の把握に使い、個別具体的なリスクの根拠はVectorDB側のテキスト記述に頼っている」というハイブリッドの現実を正確に把握した上で統合分析が行われている点**は、非常に客観的で信頼性が高い評価です。

---

### 6-2. 結論

* **VectorDB単体（5-1-4）:**
「過去に何が起き、どこから何を指摘されているか」を漏れなくキャッチアップするための「優れた議事録・レポートの要約」として機能しています。
* **GraphRAG / ハイブリッド（5-2-4）:**
その情報を単なるテキストの集まりではなく「システム設計の地図（トポロジ）」にプロットし直し、**「なぜその事故が起き、どこを直せば根本から波及を止められるか」というアーキテクチャレベルの分析**へと昇華させています。

システム障害の分析やインフラの改善計画において、単なる「文章の検索」を超えた**構造的・戦略的なインサイト**を得たい場合、ハイブリッドアプローチの優位性が明確に表れていると言えます。
