# RAG

### 1. 従来の Vector RAG（局所的・自然言語チャンク検索）が得意なケース

**質問:** 「当社の年次有給休暇の付与日数ルールと、申請期限は何日前までか教えてください。」

| 比較項目 | ① 従来の Vector RAG | ② Direct RAG (GraphDB) | ③ GraphRAG (間接RAG) |
| :--- | :--- | :--- | :--- |
| **裏側での検索処理** | 「有給休暇」「付与日数」「申請期限」に類似度が高い就業規則の**該当文章チャンク（1〜2節）**を直接取得 | 「有給休暇」に関連するノードを検索（規定文がノード化されていない場合は検索失敗） | 規定全体の事前コミュニティ要約レポート群を参照し、該当文脈を抽出・合成 |
| **実際の回答** | 「就業規則第15条に基づき、勤続年数に応じて年10日〜20日の有給休暇が付与されます。また、取得の申請は原則として**取得希望日の3日前まで**に申請システムより提出する必要があります。」 | 「データ抽出不能（または限定的回答）：`ex:LeavePolicy` に紐づく数値プロパティ `ex:minDays 10` のみを取得しました。文章表現やコンテキスト全体の解説は含まれません。」 | 「社内規定の要約によると、勤続年数に応じた有給休暇制度が存在します。申請期限を含む詳細な運用ルールについては各部門のガイドラインを参照してください。」 |
| **回答の質・課題** | **⭕ 完璧に対応可能（最も低コスト・高速）**<br>単一のドキュメント（就業規則）内に記載された文章をピンポイントで検索・引用するため、正確かつ自然な回答が最小の計算コストで得られる。 | **❌ 導入コストに対して不適切**<br>「〜の場合は〜とする」といった自然言語の細かい規定文章をすべてグラフ構造（トリプル）化するのは非効率であり、原文のニュアンスが失われやすい。 | **🔺 過剰スペック・トークン無駄遣い**<br>単なる特定の規定条文を引くだけの質問に対し、全体のコミュニティ要約を参照するため、無駄な事前ビルドコストとトークンコストが発生する。 |

### 2. GraphRAG（抽象的な全体分析）が得意なケース

**質問:** 「当社におけるセキュリティ上の懸念点や、過去の障害を踏まえた改善策を教えてください。」

| 比較項目 | ① 従来の Vector RAG | ② Direct RAG (GraphDB) | ③ GraphRAG (間接RAG) |
| :--- | :--- | :--- | :--- |
| **裏側での検索処理** | 「セキュリティ」「障害」「改善策」の単語に類似度の高い数件の文章チャンクのみを取得 | 「セキュリティ」「障害」に該当する特定ノードを検索（SPARQL生成を試行） | 事前に構築された全社のコミュニティ要約レポート群をまとめてコンテキストに投入 |
| **実際の回答** | 「2025年10月に発生したRedisのメモリ枯渇障害では、セッション保持に影響が出ました。また、一般的な改善策としてはパスワードの定期変更が推奨されます。」 | 「クエリ構文エラー（または不完全な出力）：`ex:Incident`ノードおよび `ex:SecurityPolicy`ノードに紐づく一部の事実を出力します。[データ一覧: Incident202510, Policy_VPC]`」 | 「システム全体のコミュニティ要約分析に基づき、主たる懸念点は以下の3点です。<br>1. **単一障害点:** 決済基盤（PaymentService）がRedis（SessionCache）に強く依存しており、メモリ枯渇による全社停止リスクが存在。<br>2. **権限昇格リスク:** 開発部から本番DBへのアクセス経路が冗長化されていない。<br>3. **改善策:** キャッシュ層のCluster化およびIAMポリシーの再設計が必要です。」 |
| **回答の質・課題** | **❌ 局所的で不十分**<br>たまたま検索にヒットした1〜2個の過去ログしか見えておらず、会社全体の懸念点や構造的リスクを網羅・俯瞰できていない。 | **❌ 質問に対応不能**<br>「懸念点」「改善策」といった抽象概念や全体分析はDB上の単一ノードとして存在しないため、SPARQLクエリに変換できず回答が破綻する。 | **⭕ 完璧に対応可能**<br>テキスト群から事前抽出・構造化された「全体要約（コミュニティレポート）」を読み込むため、ドキュメント群を俯瞰した総合分析・提案ができる。 |

### 3. Direct RAG / GraphDB（具体的な構造・パス検索）が得意なケース

**質問:** 「`AuthService` が停止した場合、最終的に影響を受けるすべてのサービスと、過去に発生した障害の発生原因を教えてください。」

| 比較項目 | ① 従来の Vector RAG | ② Direct RAG (GraphDB) | ③ GraphRAG (間接RAG) |
| :--- | :--- | :--- | :--- |
| **裏側での検索処理** | 「AuthService」「停止」「影響」「障害」のキーワードで類似度が高い文章数件を取得 | SPARQLで `AuthService` から伸びる依存関係パス（`ex:dependsOn*`）を100%正確に再帰追跡 | エンティティ抽出された関係性とコミュニティ要約レポートをプロンプトに投入 |
| **実際の回答** | 「AuthServiceが停止するとPaymentServiceに影響が出ます。また過去には2025年10月にRedisのメモリ枯渇による障害が発生しました。」 | 「影響を受ける全サービスは **PaymentService, OrderService, UserPortal の3件**です（漏れ率0%）。過去障害の発生原因は **SessionCache(Redis)のメモリ枯渇**（Incident202510）です。」 | 「AuthServiceの停止は、主要な依存関係であるPaymentServiceや関連するユーザー向け機能（UserPortalなど）に影響を与える可能性があります。過去にはメモリ枯渇などの障害が報告されています。」 |
| **回答の質・課題** | **❌ 漏れとハルシネーションが発生**<br>文章として近くに書かれていた`PaymentService`しか拾えず、多段の奥に接続されている`OrderService`を見落とす（網羅性の欠如）。 | **⭕ 完璧に対応可能（100%正確・高速）**<br>何段階離れたサービス（Nホップ）であっても、GraphDBのパス検索により1ミリ秒・確実（ハルシネーションゼロ）で完全な一覧を抽出。 | **🔺 曖昧で推測混じりの回答**<br>全体像の要約はできるが、グラフの末端ノードまでの「完全な網羅性」は保証されず、「〜などの可能性がある」といった確率的な表現にとどまる。 |



### 4. 「多段の依存関係と正確なファクト」を問う質問

**質問:** 「`認証機能` が停止した場合、最終的に影響を受けるすべてのサービスと、過去に発生した障害の発生原因を教えてください。」
※（`AuthService` ではなく、あえて表記揺れのある「認証機能」で質問）

| 比較項目 | ① Vector ＋ GraphDB（ハイブリッド） | ② Vector ＋ GraphRAG（ハイブリッド） |
| :--- | :--- | :--- |
| **検索メカニズム** | Vector検索で「認証機能 ≒ `ex:AuthService`」と**起点ノードを名寄せ** ➔ GraphDBで**多段パス（`dependsOn*`）を決定論的に追跡** | Vector検索で関連するテキストチャンクを取得 ＋ GraphRAGのコミュニティ要約レポートを複合参照 |
| **裏側でのデータ処理** | 起点ノード特定後は、データベースレベルで100%正確なノードリンク（`PaymentService`, `OrderService`, `UserPortal`）と障害トリプルを取得 | 類似チャンクから個別の事実を拾いつつ、全体の要約レポートから推測される影響範囲を補完合成 |
| **実際の回答** | 「『認証機能（AuthService）』の影響範囲は **PaymentService, OrderService, UserPortal の3件**です（漏れ率0%）。過去障害の原因は **SessionCache(Redis)のメモリ枯渇（Incident202510）** です。」 | 「認証機能（AuthService）の停止は、決済（PaymentService）やユーザーポータル等に影響を与える可能性があります。過去にはRedisのメモリ枯渇事故が報告されています。」 |
| **強みと評価** | **⭕ 最強の精度（表記揺れ対応 ＋ 決定論的網羅）**<br>GraphDB単体の弱点だった「表記揺れによる検索失敗」をVectorが補い、GraphDBの強みである「100%正確なNホップ追跡」を完全に活かせる**実運用における理想系**。 | **🔺 概念理解は増すが、網羅性は不完全**<br>Vectorにより直近の記述は拾いやすくなるが、GraphRAG特有の「末端ノードまで1件の漏れもなく追跡する」ことの不確実さは解消されない。 |

### 5. 「抽象的な全体分析・傾向」を問う質問

**質問:** 「当社におけるセキュリティ上の懸念点や、過去の障害を踏まえた改善策を教えてください。」

| 比較項目 | ① Vector ＋ GraphDB（ハイブリッド） | ② Vector ＋ GraphRAG（ハイブリッド） |
| :--- | :--- | :--- |
| **検索メカニズム** | Vector検索で「セキュリティ」「障害」に関する類似テキストを抽出しつつ、関連するGraphDBノードのプロパティを結合 | Vector検索で**直近・最新の個別障害ログ**を取得 ＋ GraphRAGで**システム全体の構造的リスク要約**を結合 |
| **裏側でのデータ処理** | ベクトルヒットした文章と、直結する一部の確定データ（障害ID等）を渡すが、全体を統括する集約クエリは作れない | 局所的な具体事実（Vector）と、鳥瞰的なテーマ分析（GraphRAGコミュニティレポート）を両立した統合コンテキストをLLMに渡す |
| **実際の回答** | 「2025年10月にSessionCacheのメモリ枯渇障害が発生しています。またセキュリティ規定VPC_Policyに基づき、以下のパラメータが設定されています……（全体分析は不可）」 | 「【全体分析】1. **単一障害点:** 決済基盤のRedis依存が最大の可用性リスクです。<br>【最新の個別事実】2. **直近の動き:** 先月の監査ログ（Vector取得）により、一部の権限管理で運用漏れが検知されています。」 |
| **強みと評価** | **🔺 個別ファクトは増えるが全体要約は不可**<br>Vectorがテキスト文章を拾えるため「完全な破綻」は防げるが、GraphDB側に全体を要約する構造がないため、総合的な改善提案までは作れない。 | **⭕ 最強の分析力（ミクロの事実 ＋ マクロの要約）**<br>GraphRAGが得意な「全体像・定性分析」に、Vector検索が得意な「最新・生のピンポイント記述」が合体し、**木も森も両方見える最高の回答**になる。 |
