# RAG

# 0. Goal
本リポジトリは、単体LLMの限界（ハルシネーション・非公開データの欠落）を外部ツール連携によって克服するエージェント化の過程を整理したものです。各種エージェントの分類に加え、主要ユースケースであるRAG（Vector RAG / Direct RAG / GraphRAG）の3手法を比較。クエリ特性（局所照会・依存関係追跡・構造分析）に応じた使い分けの基準を整え、RAGの実装方針を考えていくものです。後半で、GraphRAGを実装し、そのほかのRAGと結果を比較した実験をしています。

# 1. LLMの進化段階とアーキテクチャの階層

LLMは単体では**密室の対話エンジン**に過ぎず、外部システムやナレッジデータベースと連携する**Tools（外部機能）**を付与することで初めて実務利用可能な**AIエージェント**へと進化します。

実は、普段私たちがChatで使っているLLMは、正確には『Baseモデル』そのままではなく、それに学習データを加えて調整した **『Instructモデル』** です。Baseモデルはネット上の文章を読み込んで次に続く言葉を予測するだけのモデルなので、そのまま質問しても続きの文章を書き足すだけで対話になりません。

そこで、ユーザーの指示（Instruction）と理想的なAIの回答をペアにしたSFTデータや、良い回答・悪い回答を比較した選好データをBaseモデルに追加学習（ファインチューニング）させています。こうして人間と対話するAIアシスタントとして仕立て直されたのが、私たちが使っているInstructモデルです。

```text
1. Base Model（事前学習モデル：次単語予測のみ）
   │
   │ + [SFT / RLHF（指示対話の学習）]
   ▼
2. Instruct Model（単体/素のLLM：会話・指示追従が可能だが完全密室）
   │
   │ + [Tools / 外部機能の付与]
   ▼
3. AI Agent System（自律型・複合AIシステム）
   │
   ├── 【カテゴリ 1】 API Integrations（外部サービス連携：メール送信、カレンダー操作等）
   |    │
   |    ├── ① コミュニケーション・通知（メール作成・送信、Slack/Teamsへの情報共有）
   |    ├── ② スケジュール・勤怠管理（カレンダーの予定調整、打刻・勤務時間の記録）
   |    ├── ③ タスク・プロジェクト管理（Jira/Trelloのチケット起票、進捗ステータス更新）
   |    └── ④ 事務・バックオフィス処理（経費精算の自動入力、社内申請ワークフローの起動）
   |
   ├── 【カテゴリ 2】 Web Search / Browsing（リアルタイムな公開Web検索）
   └── 【カテゴリ 3】 RAG（検索拡張生成：非公開データ・専門ドキュメントの結合）
        │
        ├── ① Vector RAG（局所的なテキスト類似度検索）
        ├── ② Direct RAG / GraphDB（正確な関係性・多段の依存パス検索）
        └── ③ GraphRAG（全社文書群などの抽象的な全体像・コミュニティ要約）
```

* **単体LLM（Instruct Model）の限界:** 学習時点以降の最新情報や社内の非公開データを保持しておらず、未知のドメインに対してハルシネーション（嘘）を出力してしまう。
* **AI Agentへの進化:** 単体LLMを推論エンジン（脳）として位置づけ、外部知識を参照する**RAG**をはじめとするToolsを周囲に配置することで、信頼性の高い回答を生成可能にする。


### 1-1. AI Agent Architecture & Implementation Scope

AIエージェントシステムにおいて、LLMはテキスト推論エンジンであり、単体では外部システムへの直接アクセス能力を持ちません。エージェントの実装とは、**LLMを取り巻くアプリケーション層（MCP Client / Agent Orchestrator）を構築し、LLMにツールの存在を認識させて協調動作させること**を指します。

今日のFDE（Forward Deployed Engineer）やAIエンジニアの実務において、LLMのファインチューニングを行う機会は限られており、主要な開発領域は**このオーケストレーション層（MCP Clientの実装、ツール定義のバインディング、コンテキスト制御、状態管理）の設計・実装**が中心となっていると考えています。

#### （1）プロンプトとツール定義の送出

アプリケーション（MCPクライアント）が、ユーザーのクエリにシステムプロンプトやツール一覧（JSON Schema）を統合し、LLMの推論エンジンへ入力します。

#### （2）LLMによる判断と意図の出力

LLMがテキストの意味を解釈し、「回答にツールが必要である」と判定した場合、ツールの名前と引数を指定したJSON構造（Tool Call Intent）を出力します。※この時点ではLLMはツールを直接実行していません。

#### （3）外部ツールの代理実行

アプリケーション（MCPクライアント）がLLMから返されたJSONを解釈し、実際の外部ツール（VectorDBやGraphDBなど）へクエリを発行して処理を実行します。

#### （4）Observation（観察データ）の回収

外部ツールでの処理結果（検索結果やレスポンスデータ）がアプリケーションに返却されます。

#### （5）コンテキストの再構築と再問合せ

アプリケーションが回収したデータを会話履歴（Context）に組み込み、「このツール実行結果を踏まえて回答を作成してください」というプロンプトを構築して、再びLLMに入力します。

#### （6）最終回答の生成

LLMが入力されたObservationデータを読み込み、ユーザーの元々の質問に対する自然言語の最終回答を生成してアプリケーションへ返します。（その後、アプリからユーザーへ提示されます）

# 2. 課題解決の2つのアプローチ（RAG vs ファインチューニング）

単体LLMの「知識不足」や「ドメイン適応」を補うアプローチとして、外部ツール連携である**RAG**と、モデル自体の重みを書き換える**ファインチューニング（FT）**が存在します。

| 手法 | 特徴と役割 | コストと運用の特徴 |
| :--- | :--- | :--- |
| **RAG<br>(検索拡張生成)** | **外部の辞書を引きながら答える**手法。<br>社内文書やDBを検索し、その結果をプロンプトに含めてLLMに回答させる。 | **運用低コスト・即時更新**<br>DBを書き換えるだけで最新情報が反映される。初期学習コストは不要だが、検索精度に依存する。 |
| **Fine-Tuning<br>(事前学習の微調整)** | **脳の構造（モデルの重み）を書き換える**手法。<br>特定の専門用語、口調、出力フォーマット（JSON等）をモデル自体に定着させる。 | **初期高コスト・更新難**<br>GPUリソースと高品質な学習データが必要。事実の追加・更新には再学習が必要なため、最新ナレッジの保持には不向き。 |

# 3. RAGカテゴリの選定基準

本リポジトリで扱う **【カテゴリ 4】 RAG** においては、要求されるデータ構造と問いの抽象度に応じて使い分けを行います。

1. **Vector RAG（局所的・自然言語検索）**
   * **用途:** 就業規則やマニュアルなど、1つの文書・章節の中に答えが完結しているFAQ型検索。
2. **Direct RAG / GraphDB（構造的・決定論的パス検索）**
   * **用途:** インフラ構成、依存関係、組織階層など、多段階のリンク（Nホップ）を辿り、漏れなく100%正確に追跡するデータ検索。
3. **GraphRAG（抽象的・全体像要約）**
   * **用途:** 「組織全体の課題は？」「過去数年のトレンドは？」など、事前抽出されたコミュニティ要約を用いてドキュメント群全体を鳥瞰分析する検索。

### 3-1. 従来の Vector RAG（局所的・自然言語チャンク検索）が得意なケース

**質問:** 「当社の年次有給休暇の付与日数ルールと、申請期限は何日前までか教えてください。」

| 比較項目 | ① 従来の Vector RAG | ② Direct RAG (GraphDB) | ③ GraphRAG (間接RAG) |
| :--- | :--- | :--- | :--- |
| **裏側での検索処理** | 「有給休暇」「付与日数」「申請期限」に類似度が高い就業規則の**該当文章チャンク（1〜2節）**を直接取得 | 「有給休暇」に関連するノードを検索（規定文がノード化されていない場合は検索失敗） | 規定全体の事前コミュニティ要約レポート群を参照し、該当文脈を抽出・合成 |
| **実際の回答** | 「就業規則第15条に基づき、勤続年数に応じて年10日〜20日の有給休暇が付与されます。また、取得の申請は原則として**取得希望日の3日前まで**に申請システムより提出する必要があります。」 | 「データ抽出不能（または限定的回答）：`ex:LeavePolicy` に紐づく数値プロパティ `ex:minDays 10` のみを取得しました。文章表現やコンテキスト全体の解説は含まれません。」 | 「社内規定の要約によると、勤続年数に応じた有給休暇制度が存在します。申請期限を含む詳細な運用ルールについては各部門のガイドラインを参照してください。」 |
| **回答の質・課題** | **⭕ 完璧に対応可能（最も低コスト・高速）**<br>単一のドキュメント（就業規則）内に記載された文章をピンポイントで検索・引用するため、正確かつ自然な回答が最小の計算コストで得られる。 | **❌ 導入コストに対して不適切**<br>「〜の場合は〜とする」といった自然言語の細かい規定文章をすべてグラフ構造（トリプル）化するのは非効率であり、原文のニュアンスが失われやすい。 | **🔺 過剰スペック・トークン無駄遣い**<br>単なる特定の規定条文を引くだけの質問に対し、全体のコミュニティ要約を参照するため、無駄な事前ビルドコストとトークンコストが発生する。 |

### 3-2. GraphRAG（抽象的な全体分析）が得意なケース

**質問:** 「当社におけるセキュリティ上の懸念点や、過去の障害を踏まえた改善策を教えてください。」

| 比較項目 | ① 従来の Vector RAG | ② Direct RAG (GraphDB) | ③ GraphRAG (間接RAG) |
| :--- | :--- | :--- | :--- |
| **裏側での検索処理** | 「セキュリティ」「障害」「改善策」の単語に類似度の高い数件の文章チャンクのみを取得 | 「セキュリティ」「障害」に該当する特定ノードを検索（SPARQL生成を試行） | 事前に構築された全社のコミュニティ要約レポート群をまとめてコンテキストに投入 |
| **実際の回答** | 「2025年10月に発生したRedisのメモリ枯渇障害では、セッション保持に影響が出ました。また、一般的な改善策としてはパスワードの定期変更が推奨されます。」 | 「クエリ構文エラー（または不完全な出力）：`ex:Incident`ノードおよび `ex:SecurityPolicy`ノードに紐づく一部の事実を出力します。[データ一覧: Incident202510, Policy_VPC]`」 | 「システム全体のコミュニティ要約分析に基づき、主たる懸念点は以下の3点です。<br>1. **単一障害点:** 決済基盤（PaymentService）がRedis（SessionCache）に強く依存しており、メモリ枯渇による全社停止リスクが存在。<br>2. **権限昇格リスク:** 開発部から本番DBへのアクセス経路が冗長化されていない。<br>3. **改善策:** キャッシュ層のCluster化およびIAMポリシーの再設計が必要です。」 |
| **回答の質・課題** | **❌ 局所的で不十分**<br>たまたま検索にヒットした1〜2個の過去ログしか見えておらず、会社全体の懸念点や構造的リスクを網羅・俯瞰できていない。 | **❌ 質問に対応不能**<br>「懸念点」「改善策」といった抽象概念や全体分析はDB上の単一ノードとして存在しないため、SPARQLクエリに変換できず回答が破綻する。 | **⭕ 完璧に対応可能**<br>テキスト群から事前抽出・構造化された「全体要約（コミュニティレポート）」を読み込むため、ドキュメント群を俯瞰した総合分析・提案ができる。 |

### 3-3. Direct RAG / GraphDB（具体的な構造・パス検索）が得意なケース

**質問:** 「`AuthService` が停止した場合、最終的に影響を受けるすべてのサービスと、過去に発生した障害の発生原因を教えてください。」

| 比較項目 | ① 従来の Vector RAG | ② Direct RAG (GraphDB) | ③ GraphRAG (間接RAG) |
| :--- | :--- | :--- | :--- |
| **裏側での検索処理** | 「AuthService」「停止」「影響」「障害」のキーワードで類似度が高い文章数件を取得 | SPARQLで `AuthService` から伸びる依存関係パス（`ex:dependsOn*`）を100%正確に再帰追跡 | エンティティ抽出された関係性とコミュニティ要約レポートをプロンプトに投入 |
| **実際の回答** | 「AuthServiceが停止するとPaymentServiceに影響が出ます。また過去には2025年10月にRedisのメモリ枯渇による障害が発生しました。」 | 「影響を受ける全サービスは **PaymentService, OrderService, UserPortal の3件**です（漏れ率0%）。過去障害の発生原因は **SessionCache(Redis)のメモリ枯渇**（Incident202510）です。」 | 「AuthServiceの停止は、主要な依存関係であるPaymentServiceや関連するユーザー向け機能（UserPortalなど）に影響を与える可能性があります。過去にはメモリ枯渇などの障害が報告されています。」 |
| **回答の質・課題** | **❌ 漏れとハルシネーションが発生**<br>文章として近くに書かれていた`PaymentService`しか拾えず、多段の奥に接続されている`OrderService`を見落とす（網羅性の欠如）。 | **⭕ 完璧に対応可能（100%正確・高速）**<br>何段階離れたサービス（Nホップ）であっても、GraphDBのパス検索により1ミリ秒・確実（ハルシネーションゼロ）で完全な一覧を抽出。 | **🔺 曖昧で推測混じりの回答**<br>全体像の要約はできるが、グラフの末端ノードまでの「完全な網羅性」は保証されず、「〜などの可能性がある」といった確率的な表現にとどまる。 |


# 4. ハイブリッドなRAG

### 4-1. 多段の依存関係と正確なファクトを問う質問

**質問:** 「`認証機能` が停止した場合、最終的に影響を受けるすべてのサービスと、過去に発生した障害の発生原因を教えてください。」
※（`AuthService` ではなく、あえて表記揺れのある「認証機能」で質問）

| 比較項目 | ① Vector ＋ GraphDB（ハイブリッド） | ② Vector ＋ GraphRAG（ハイブリッド） |
| :--- | :--- | :--- |
| **検索メカニズム** | Vector検索で「認証機能 ≒ `ex:AuthService`」と**起点ノードを名寄せ** ➔ GraphDBで**多段パス（`dependsOn*`）を決定論的に追跡** | Vector検索で関連するテキストチャンクを取得 ＋ GraphRAGのコミュニティ要約レポートを複合参照 |
| **裏側でのデータ処理** | 起点ノード特定後は、データベースレベルで100%正確なノードリンク（`PaymentService`, `OrderService`, `UserPortal`）と障害トリプルを取得 | 類似チャンクから個別の事実を拾いつつ、全体の要約レポートから推測される影響範囲を補完合成 |
| **実際の回答** | 「『認証機能（AuthService）』の影響範囲は **PaymentService, OrderService, UserPortal の3件**です（漏れ率0%）。過去障害の原因は **SessionCache(Redis)のメモリ枯渇（Incident202510）** です。」 | 「認証機能（AuthService）の停止は、決済（PaymentService）やユーザーポータル等に影響を与える可能性があります。過去にはRedisのメモリ枯渇事故が報告されています。」 |
| **強みと評価** | **⭕ 最強の精度（表記揺れ対応 ＋ 決定論的網羅）**<br>GraphDB単体の弱点だった「表記揺れによる検索失敗」をVectorが補い、GraphDBの強みである「100%正確なNホップ追跡」を完全に活かせる**実運用における理想系**。 | **🔺 概念理解は増すが、網羅性は不完全**<br>Vectorにより直近の記述は拾いやすくなるが、GraphRAG特有の「末端ノードまで1件の漏れもなく追跡する」ことの不確実さは解消されない。 |

### 4-2. 抽象的な全体分析・傾向を問う質問

**質問:** 「当社におけるセキュリティ上の懸念点や、過去の障害を踏まえた改善策を教えてください。」

| 比較項目 | ① Vector ＋ GraphDB（ハイブリッド） | ② Vector ＋ GraphRAG（ハイブリッド） |
| :--- | :--- | :--- |
| **検索メカニズム** | Vector検索で「セキュリティ」「障害」に関する類似テキストを抽出しつつ、関連するGraphDBノードのプロパティを結合 | Vector検索で**直近・最新の個別障害ログ**を取得 ＋ GraphRAGで**システム全体の構造的リスク要約**を結合 |
| **裏側でのデータ処理** | ベクトルヒットした文章と、直結する一部の確定データ（障害ID等）を渡すが、全体を統括する集約クエリは作れない | 局所的な具体事実（Vector）と、鳥瞰的なテーマ分析（GraphRAGコミュニティレポート）を両立した統合コンテキストをLLMに渡す |
| **実際の回答** | 「2025年10月にSessionCacheのメモリ枯渇障害が発生しています。またセキュリティ規定VPC_Policyに基づき、以下のパラメータが設定されています……（全体分析は不可）」 | 「【全体分析】1. **単一障害点:** 決済基盤のRedis依存が最大の可用性リスクです。<br>【最新の個別事実】2. **直近の動き:** 先月の監査ログ（Vector取得）により、一部の権限管理で運用漏れが検知されています。」 |

# 5. RAGの比較実験

以下の架空のドキュメントをもとに、VectorDBとグラフナレッジを作成します。
```
=== インフラ・開発チーム雑記＆障害振り返りメモ（未整理） ===

・2025/10/12 インシデント振り返り (INC-202510)
AuthServiceのレスポンスが突如激重になり全系停止した件。
原因調べたら、認証セッションの保持に使ってるRedis（SessionCache）がメモリ溢れ（OOM Kill）起こしてた。セッション検証がタイムアウトしてAuthServiceが死んだのが引き金。
これ、そもそもSessionCacheが1台構成なのが諸悪の根源。マルチAZでクラスタ化して、一時キャッシュとセッションデータ分けようって話出てるけど放置されてる。あと、AuthService死んだときに後続サービスが巻き添え喰らわないようにサーキットブレーカー入れないとまた同じこと起きるぞ。

・依存関係の走り書き（仕様書が古いので各自確認のこと）
- UserPortalはログインのためにAuthService叩く。あと注文履歴表示でOrderService呼んでる。
- OrderServiceは受注時にPaymentServiceのレスポンス待ってから処理進める。
- PaymentServiceは決済トークンの有効性チェックで毎回AuthServiceを直接叩いてる。
- NotificationServiceはOrderServiceからのイベントフックで動いてメール飛ぶ仕組み。

・2024/05/18 インシデント振り返り (INC-202405)
PaymentServiceでスロークエリ多発してDBコネクションが枯渇。
原因は決済履歴テーブルのインデックス貼り忘れ。PaymentServiceが詰まったせいで、レスポンス待ちのOrderServiceも詰まり、最終的にNotificationServiceまで非同期キューが溢れて止まった。
DBのインデックス見直しと定期的なスロークエリモニタリング、コネクションプールのチューニングを改善タスクに入れること。

・2026/01/22 インシデント振り返り (INC-202601)
NotificationService経由のメール送信が全部エラーになった件。
原因は外部APIキーの有効期限切れと、サービス間通信で使ってるIAMロールのポリシー設定ミス。IAMポリシーで `resource: "*"` になってて過剰権限だったから、作業者が意図しないリソースを上書き操作できちゃったのが直接のトリガー。
対策としては、ワイルドカード（*）の全廃と最小権限の原則（PoLP）徹底。IAMロールの定期監査タスクを組む。

・セキュリティ監査の指摘事項（メモ）
本番環境（ProdDB）へのアクセス経路がガバガバ。開発VPCから直接ProdDBにアクセスできるルートが残ってるのヤバすぎる。アクセス経路絞って、Bastion（踏み台）経由＋VPC Peeringで厳格に分離してくれ。
あと上述の通り、IAMポリシーで権限与えすぎ問題と、AuthService/SessionCache周辺のSPOF（単一障害点）放置は早急にインフラチームで対応すること。
```

## セキュリティ上の懸念点

**1. IAMポリシーの過剰権限（ワイルドカード設定）**
INC-202601で、サービス間通信用のIAMロールに `resource: "*"` という過剰な権限が設定されており、これが原因で作業者が意図しないリソースを上書きできてしまう状態でした。この設定ミスと外部APIキーの期限切れが重なり、NotificationServiceのメール送信が全滅する障害に直結しています。

**2. 本番環境（ProdDB）へのアクセス経路の不備**
セキュリティ監査で、開発VPCから本番DBへ直接アクセスできる経路が残っていることが指摘されています。Bastion経由・VPC Peeringによる厳格な分離ができていません。

**3. AuthService/SessionCache周辺のSPOF（単一障害点）**
SessionCache（Redis）が1台構成のままで、マルチAZクラスタ化の話が出ているにもかかわらず放置されています。INC-202510では、このSessionCacheのOOM KillがAuthServiceの全系停止を招きました。

## 過去の障害を踏まえた改善策

**INC-202510（AuthService全系停止）関連**
- SessionCacheのマルチAZクラスタ化、一時キャッシュとセッションデータの分離
- AuthService障害時に後続サービス（PaymentService等）が巻き添えにならないよう、サーキットブレーカーの導入

**INC-202405（PaymentServiceのDBコネクション枯渇）関連**
- 決済履歴テーブルのインデックス見直し
- 定期的なスロークエリモニタリングの実施
- コネクションプールのチューニング

**INC-202601（IAM設定ミスによるメール送信障害）関連**
- ワイルドカード（`*`）権限の全廃
- 最小権限の原則（PoLP）の徹底
- IAMロールの定期監査タスクの新設

**セキュリティ監査指摘事項関連**
- 本番DBへのアクセス経路をBastion経由＋VPC Peeringに厳格化し、開発VPCからの直接アクセスを遮断

---

サービス依存関係（UserPortal→AuthService/OrderService、OrderService→PaymentService、PaymentService→AuthService、NotificationService←OrderServiceイベント）を見ると、**AuthServiceとPaymentServiceが障害連鎖の起点になりやすい構造**であることも分かります。特にAuthServiceは複数サービスから直接叩かれているため、SPOF解消とサーキットブレーカー導入が優先度高めと言えそうです。

## セキュリティ上の懸念点

**1. IAM権限の過剰付与（ワイルドカード設定）**
グラフ上では `Inc-202601 --AFFECTED_BY--> Iamロール --AFFECTED_BY--> Resource: "*"` という因果連鎖が明示されており、VectorDB側もこれを裏付けています。サービス間通信用IAMロールに `resource: "*"` が設定され過剰権限状態となり、作業者が意図しないリソースを上書き操作できてしまったことがINC-202601の直接トリガーでした。

**2. 本番DB（ProdDB）へのアクセス経路の不備**
グラフでは `開発Vpc --CONNECTION--> Proddb`、`Proddb --CONNECTION--> Bastion/Iamポリシー` という関係が抽出されており、開発VPCから本番DBへ直接アクセスできる経路が残存していることが構造的にも確認できます。Bastion＋VPC Peeringでの分離が未完了です。

**3. AuthService/SessionCache周辺のSPOF（単一障害点）**
グラフの `権限 --CONNECTION--> Spof --CONNECTION--> インフラチーム` という接続、および `Sessioncache --CAUSED_BY--> マルチAz --IMPLIES--> クラスタ化` という関係が示す通り、SessionCacheが1台構成のままクラスタ化が放置されている点がIAM問題と並んで「インフラチーム早急対応事項」として括られています。

## 過去の障害を踏まえた改善策

| インシデント | 根本原因（グラフ上の因果） | 改善策 |
|---|---|---|
| INC-202510（AuthService全系停止） | `Inc-202510 --CAUSED_BY--> Oom Kill`／`Authservice --NEEDS--> サーキットブレーカー` | SessionCacheのマルチAZクラスタ化、一時キャッシュとセッションデータの分離、AuthService障害時の後続サービス巻き添え防止のためサーキットブレーカー導入 |
| INC-202405（PaymentService詰まり） | `Db --CONTAINS--> インデックス --CONTAINS--> インデックス見直し／定期的なスロークエリモニタリング／チューニング` | DBインデックス見直し、定期的なスロークエリモニタリング、コネクションプールのチューニング |
| INC-202601（メール送信全滅） | `Inc-202601 --CAUSED_BY--> 過剰権限／上書き操作` | ワイルドカード権限の全廃、最小権限の原則（PoLP）徹底、IAMロールの定期監査タスク新設 |
| セキュリティ監査指摘 | `開発Vpc --CONNECTION--> Proddb`（直接経路残存） | Bastion経由＋VPC Peeringによる厳格なアクセス経路分離 |

## サービス依存構造からの示唆
グラフの `Userportal --CALLS--> Authservice/Orderservice`、`Orderservice --CALLS--> Paymentservice/Notificationservice` という呼び出し関係から、**AuthServiceとOrderServiceがハブとなって障害を連鎖させやすい構造**であることが分かります。実際、PaymentServiceの詰まりがOrderService経由でNotificationServiceまで波及した（INC-202405）ように、この依存構造を放置するとSPOF解消をしてもボトルネックが移動するだけになりかねません。**サーキットブレーカーの導入はAuthServiceだけでなくOrderService⇄PaymentService間にも広げる**ことが望ましいと考えられます。


# 6. 結果の比較
VectorDB単体でも過去障害の事実や個別対策を網羅できていますが、GraphRAG（＋VectorDB）を突き合わせた結果は「多段依存の追跡」と「システム全体の構造的インサイトの導出」において決定的な差が現れています。

両者の比較における主な違いは以下の通りです。

### 6-1. 多段依存関係の連結・追跡能力

VectorDB単体: 

チャンク内に書かれた「UserPortal→AuthService」や「PaymentService→AuthService」といった局所的な関係性を文字列として拾い出し、要約しています。

GraphRAG結合: 

Userportal --CALLS--> Authservice/Orderservice から Orderservice --CALLS--> Paymentservice/Notificationservice という複数チャンクに跨るノード・エッジを連結し、障害が末端の NotificationService まで波及する長鎖の連鎖経路を構造的に再現しています。

### 6-2. 構造的インサイト（提案の質）の深さ

VectorDB単体: 

ドキュメントに記載された各障害の改善策（Redisクラスタ化、IAMワイルドカード廃止など）を素直に箇条書きで並べるにとどまります。

GraphRAG結合: 

グラフの呼び出し構造全体を俯瞰し、「AuthServiceのSPOFを解消しても、依存構造上ボトルネックが OrderService ↔ PaymentService に移動するだけになる」という、テキストに直接書かれていない大域的なリスクと改善提案（サーキットブレーカー適用範囲の拡大） を自発的に導出できています。

### 6-3. 因果関係の説明性（Explainability）

VectorDB単体: 

類似テキストをまとめた文章回答となるため、なぜその改善策が必要なのかの根拠が文章に依存します。

GraphRAG結合: 

Inc-202601 --AFFECTED_BY--> Iamロール --AFFECTED_BY--> Resource: "*" のように、事象・リソース・原因のグラフパスが提示されるため、判定根拠が極めて明確かつ追尾可能です。

単純な事実抽出や個別対策のリストアップであればVectorDBのみでも実用レベルですが、本件のように「システム間の複雑な相互作用」や「隠れたボトルネックの特定」が求められるシチュエーションでは、関係性を構造として保持するGraphRAGの優位性が明確に出ています。
